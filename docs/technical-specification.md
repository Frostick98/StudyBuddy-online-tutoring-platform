# Технічне завдання: StudyBuddy

Версія 1.0 від 31.10.2026. Стандарт: SRS (IEEE 830 / ISO/IEC/IEEE 29148). Автор: Висоцький Олександр.

## 1. Вступ

**1.1 Мета документа.** Документ формалізує вимоги до Web-платформи StudyBuddy і є основою для планування спринтів, розробки й тестування.

**1.2 Область застосування.** StudyBuddy - Web-платформа, що поєднує учнів і репетиторів: пошук, бронювання занять, онлайн-оплата та проведення занять з відеозв'язком або чатом. Поза межами проєкту: мобільні застосунки, офлайн-режим, власна платіжна система.

**1.3 Визначення й скорочення.** FR/NFR - функціональна / нефункціональна вимога; MoSCoW - метод пріоритезації (Must, Should, Could, Won't); UC - Use Case; CI - безперервна інтеграція; DoD - Definition of Done; MVP - мінімально життєздатний продукт; ADR - запис архітектурного рішення.

**1.4 Посилання.** IEEE 830-1998; ISO/IEC/IEEE 29148; [docs/sdlc](sdlc/); [docs/board](board/); [docs/adr](adr/).

## 2. Загальний опис

**2.1 Перспектива продукту.** StudyBuddy - нова самостійна система: клієнтська частина в браузері, серверна частина на C# / ASP.NET Core, база даних і зовнішні сервіси (платіжний шлюз, email, відеозв'язок). Тип системи та стек обґрунтовано в [ADR-0001](adr/0001-web-zastosunok-yak-typ-systemy.md) і [ADR-0002](adr/0002-stek-csharp-aspnet-core.md).

**2.2 Основні функції.** Реєстрація й профілі; пошук репетиторів за предметом і ціною; календар доступності; бронювання; email-сповіщення; онлайн-оплата й історія платежів; відеозв'язок і чат; відгуки та рейтинги.

**2.3 Цілі проєкту (вимірювані).**

- Скоротити шлях учня від входу до підтвердженого бронювання до ≤ 3 хв у 90 % випадків протягом місяця після релізу.
- Забезпечити, щоб не менше 80 % бронювань оплачувалися онлайн протягом двох місяців після запуску оплати.
- Отримувати відгук щонайменше за 30 % проведених занять протягом двох місяців після запуску відгуків.
- Випустити MVP у production до кінця 12-го тижня проєкту (6 спринтів по 2 тижні).

**2.4 Характеристики користувачів.** Учень шукає репетитора й не потребує технічної підготовки. Репетитор надає послуги, веде календар і заняття. Адміністратор (замовник) стежить за роботою платформи. Команда розробки - 4 особи (Product Owner/аналітик, 2 розробники, QA-інженер).

**2.5 Припущення й залежності.** Користувачі мають стабільний інтернет і сучасний браузер. Оплата залежить від зовнішнього платіжного шлюзу, сповіщення - від сервісу електронної пошти. Вимоги можуть змінюватися за відгуками замовника, тому Backlog переглядається щоспринту.

## 5. Технічні обмеження та стек технологій

- Тип системи: Web, доступ через браузер ([ADR-0001](adr/0001-web-zastosunok-yak-typ-systemy.md)).
- Серверна частина: C# та ASP.NET Core ([ADR-0002](adr/0002-stek-csharp-aspnet-core.md)); сервер із підтримкою .NET runtime (Windows або Linux).
- Інструменти розробки: Git і GitHub, GitHub Projects (дошка Kanban), Markdown (документація), CI на кожен push.
- Зовнішні сервіси: платіжний шлюз (PCI DSS), сервіс email-розсилок, сервіс відеозв'язку в браузері.
- База даних: ще не обрана, модель даних проєктується (ERD: users, tutors, bookings, задача T-005); вибір буде зафіксований окремим ADR.
- Обмеження проєкту: команда 4 особи, 3 місяці, 6 спринтів.

## 6. Критерії прийнятності

Критерій прийнятності перевіряє одну вимогу. Нижче - сценарії Given-When-Then для ключових вимог.

| Сценарій | Опис |
| --- | --- |
| AC-1 (FR-001) | **Given:** користувач відкрив форму реєстрації й вказав email, якого ще немає в системі, та пароль із 8+ символів. **When:** натискає «Зареєструватися». **Then:** акаунт створюється, користувач потрапляє на сторінку свого профілю за ≤ 2 с. |
| AC-2 (FR-004) | **Given:** у системі є репетитори з предметом «Математика» і ціною від 200 до 600 грн. **When:** учень шукає «Математика» з ціною до 300 грн. **Then:** у списку лише репетитори з ціною до 300 грн, результат з'являється за ≤ 2 с. |
| AC-3 (FR-006) | **Given:** репетитор має вільний слот, який учень A уже забронював. **When:** учень B намагається забронювати цей самий слот. **Then:** система відхиляє бронювання повідомленням «слот зайнятий» і не створює дубль. |
| AC-4 (FR-008) | **Given:** учень має бронювання зі статусом «Очікує оплати». **When:** оплачує його коректною карткою. **Then:** статус змінюється на «Оплачено» за ≤ 5 с, учень отримує підтвердження. |
| AC-5 (FR-010) | **Given:** розробник робить push коміту з тестом, що не проходить. **When:** запускається CI-пайплайн. **Then:** збірка позначається як невдала, злиття цієї гілки в main заблоковане. |

## 7. Definition of Done для релізу

Definition of Done визначає готовність усього релізу, а не однієї вимоги. Реліз готовий, якщо:

- усі вимоги Must (FR-001 - FR-006, FR-008, FR-010, FR-011) реалізовані, а їхні критерії прийнятності виконуються;
- усі сценарії AC-1 - AC-5 пройдені в тестовому середовищі й зафіксовані в Test Report;
- усі автотести проходять у CI, а покриття тестами модуля автентифікації становить не менше 70 %;
- немає відкритих дефектів із пріоритетом Critical або High;
- код злито в main після Code Review щонайменше одним іншим членом команди, без конфліктів;
- застосунок розгорнуто на staging і пройдено ручну перевірку основного сценарію: реєстрація - пошук - бронювання - оплата - заняття;
- підготовлено документацію: README з інструкцією розгортання, журнал ADR, Release Notes і коротка інструкція користувача;
- виконано вимоги NFR-P-001, NFR-S-001 - NFR-S-003: перевірено вимірюваннями або перевіркою конфігурації.
