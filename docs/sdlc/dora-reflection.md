# DORA-рефлексія

## Deployment Frequency

Roadmap побудовано на спринтах по два тижні, кожен з яких завершується релізом
інкременту на staging, а після Sprint 3 — і на production. Такий ритм наближає
команду до частих, передбачуваних релізів замість рідкісних великих постачань,
характерних для Waterfall, що є першим кроком до рівня Elite за цією метрикою.

## Lead Time for Changes

Дрібні, оцінювані задачі на дошці (наприклад, T-001–T-004 замість абстрактного
«зробити бекенд») дозволяють задачам швидко проходити колонки In Progress → Review →
Done без затримок на з'ясування обсягу роботи. Налаштований CI-пайплайн (T-004)
автоматично збирає й тестує код при кожному push, скорочуючи час між написанням
коду та готовністю до релізу.

## Change Failure Rate

Обов'язковий Code Review та проходження автотестів, зафіксовані в Definition of Done,
знижують імовірність потрапляння дефектів у production. Окрема мітка Bug з
пріоритетами дає змогу команді бачити й блокувати реліз, якщо існують критичні
відкриті дефекти, перш ніж зміни потраплять у production.

## MTTR (Mean Time to Recovery)

Дрібні за обсягом задачі та часті релізи означають, що в разі збою відкат чи
виправлення стосується невеликого набору змін, а не місяців роботи, що спрощує
локалізацію причини. Колонка Review та наявність Release Notes/Changelog дозволяють
команді швидко визначити, яка саме зміна спричинила інцидент, і оперативно випустити
патч у межах поточного або позапланового спринту.
