# Вибір моделі SDLC

## Картка проєкту

| Поле | Значення |
| --- | --- |
| Назва проєкту | StudyBuddy — платформа для онлайн-репетиторства |
| Тип системи | Web |
| Замовник | Освітній стартап StudyBuddy (приватний замовник, не держустанова) |
| Розмір команди | 4 особи (Product Owner/аналітик, 2 розробники, QA-інженер) |
| Очікуваний термін | 3 місяці (6 спринтів по 2 тижні) |
| Стабільність вимог | Можуть змінюватись (замовник уточнює функціонал за відгуками користувачів) |

## Оцінка проєкту за критеріями

| Критерій проєкту | Відповідь | Орієнтовна модель / метод |
| --- | --- | --- |
| Вимоги стабільні, замовник — держустанова | Ні — замовник приватний стартап, вимоги уточнюються | — |
| Потрібна формальна верифікація (критична система) | Ні — система не є критичною для життя/безпеки | — |
| Вимоги уточнюються ітераційно, ОО-аналіз і проєктування | Частково — є елементи ітеративності | Ітераційна модель (RUP) — не обрано |
| Високі ризики, великий інноваційний проєкт | Ні — типовий, не надто ризикований проєкт | — |
| Команда невелика, потрібні регулярні часті релізи | Так — 4 особи, потрібен швидкий зворотний зв'язок від замовника | Scrum / Kanban — Гнучкі (Agile) |

## Обґрунтування вибору

Для проєкту StudyBuddy обрано Scrum-модель SDLC, оскільки команда невелика (4 особи),
а замовник — приватний стартап, який очікує перших результатів і зворотного зв'язку
вже через кілька тижнів, а не після місяців розробки. Вимоги до платформи не є повністю
зафіксованими: після демонстрації прототипу замовник регулярно коригує пріоритети
функцій (наприклад, формат оплати занять чи механізм підбору репетитора), що робить
Waterfall і V-модель непридатними через їхню низьку толерантність до змін вимог після
затвердження фази.

Проєкт не є критичною системою (немає вимог до формальної верифікації чи сертифікації),
тому важка документаційна модель на кшталт V-моделі є невиправданою за співвідношенням
витрат і ризиків. Спіральна модель орієнтована на проєкти з високим інноваційним
ризиком і вимагає ресурсів на повноцінний аналіз ризику на кожній ітерації, чого не
потребує відносно типовий продукт такого масштабу.

Scrum дозволяє командою з чотирьох людей ітеративно постачати робочий інкремент кожні
два тижні, отримувати відгук замовника й гнучко перепріоритизувати Backlog без зупинки
всього процесу розробки. Отже, за критеріями гнучкості вимог, розміру команди та
помірного рівня ризику Scrum є моделлю, що найкраще балансує швидкість постачання
цінності та керованість проєкту.
