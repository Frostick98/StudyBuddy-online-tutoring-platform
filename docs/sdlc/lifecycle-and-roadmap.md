# Фази життєвого циклу та дорожня карта

## Фази життєвого циклу

| Фаза | Зміст | Тривалість | Артефакти | Відповідальний |
| --- | --- | --- | --- | --- |
| Аналіз вимог | Збір і уточнення вимог замовника, формування Backlog | Щоспринту (перегляд і поповнення Backlog) | Backlog вимог, User Stories, матриця трасованості | Product Owner |
| Проєктування | Архітектура застосунку, модель даних, UI/UX | Щоспринту (перед розробкою відповідних задач) | ERD, UML Component-діаграма, Wireframes, API-специфікація (OpenAPI) | Тімлід / розробники |
| Розробка | Кодування функціоналу згідно з User Stories спринту | Щоспринту, 2 тижні | Вихідний код у репозиторії, юніт-тести, записи Code Review | Розробники |
| Тестування | Перевірка якості, пошук дефектів | Щоспринту, паралельно з розробкою + Sprint Review | Test Plan, Test Report, реєстр дефектів (Buglist) | QA-інженер |
| Розгортання | Постачання інкременту на staging/production | Наприкінці кожного спринту | Release Notes, CI/CD pipeline, робочий застосунок (build) | DevOps / тімлід |
| Супровід | Підтримка після релізу, обробка зворотного зв'язку | Постійно після першого релізу (Sprint 3+) | Changelog, патчі, звіти про інциденти | Вся команда |

## Дорожня карта (Roadmap)

| Спринт | Тижні | Фокус |
| --- | --- | --- |
| Sprint 0 | Тиждень 1 | Ініціація: картка проєкту, Backlog, архітектура, налаштування дошки задач і репозиторію |
| Sprint 1 | Тижні 2–3 | Реєстрація/автентифікація користувачів, базовий профіль репетитора та учня |
| Sprint 2 | Тижні 4–5 | Пошук і підбір репетитора, календар доступності |
| Sprint 3 | Тижні 6–7 | Бронювання заняття, сповіщення; перший release на staging |
| Sprint 4 | Тижні 8–9 | Онлайн-оплата занять, історія платежів |
| Sprint 5 | Тижні 10–11 | Відеозв'язок/чат для проведення заняття, відгуки та рейтинги |
| Sprint 6 | Тижні 12 | Стабілізація, виправлення дефектів, реліз у production |

## Узгодженість з обраною моделлю

Оскільки обрано Scrum, Roadmap організовано спринтами по два тижні, а не жорсткими
послідовними фазами: аналіз, проєктування, розробка й тестування повторюються в межах
кожного спринту, а не виконуються один раз для всього проєкту. Формального
затвердження кожної фази перед переходом до наступної (як у Waterfall) немає —
натомість наприкінці кожного спринту відбувається Sprint Review, на якому замовник
переглядає інкремент і коригує пріоритети наступного спринту.
